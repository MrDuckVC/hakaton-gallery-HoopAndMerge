## 1. Совместная работа frontend/backend

HTTP остаётся `/api/v1`, WS `/api/v1/ws`, cookie/Origin/ошибки/единственный writer — как в contract.md.
Протокол 1 расширяется новыми событиями без изменения старых payload. Manifest может
содержать необязательное `extensions: ["sunday_v1"]`; сервер объявляет его только после
подключения всего расширения. Отсутствие поля означает базовый API. Не создавать legacy aliases.
Фронт заранее реализует расширение по fixtures; пока capability отсутствует, новые функции не показывает.
Фронтенд находится в отдельном репозитории: скопировать `sunday.types.ts`, читать этот документ,
OpenAPI и схемы WS; не переносить frontend source в backend. Fixtures — `examples/sunday/`.

Первое событие всё ещё world.snapshot. За ним сервер ставит world.runtime, затем npc.state,
затем остальные новые события. При переходе world.entered опережает world.runtime/npc.state нового зала.
Фронт блокирует действия, выгружает старый зал и его runtime/NPC, загружает пакет и применяет
полученный runtime, затем отправляет прежний world.ready. Сервер не меняет epoch при правке оформления.
Новые события состояния несут room_id/world_version прямо либо во вложенном runtime; устаревший зал/версию клиент отбрасывает.
room.sync ответы содержат request_id; спонтанные runtime/NPC/probe — без него.
Первый runtime текущего зала применяется независимо от revision; дальнейшие — только с большей revision.
Это полные снимки, не patches: потерянное промежуточное обновление не требует replay.
В новой вкладке/после reconnect сервер снова отдаёт полное состояние; не повторять автоматически
неподтверждённые команды. После отправки ошибочной/потерянной команды UI перечитывает снимок
через `room.sync` с новым UUID. Ответ только отправителю: world.runtime, затем npc.state.

## 2. Статический мир и сохраняемый runtime

JSON/изображения C01 и WORLD_VERSION неизменны. Runtime overlay хранится в PostgreSQL,
ключ `(world_version,room_id)`, revision начинается с 1, положительное safe integer.
Новая WORLD_VERSION получает новые значения по умолчанию; старые overlays не удаляются и не
переносятся автоматически. Файлы C01/миграции 00001–00005 не редактировать.

RoomConfig: цвет оформления `accent_color`, свет `lighting=neutral|warm|cool`,
`guide_placements` всех и только существующих в зале гидов, ровно два `lamp_slots`
с ID `a`,`b`, `npc_count` 0–10, `installation_visible`. Типы/структура — схемы и TS.
Для guide placements `rotation_y ∈ [−π, π)`, как в машинных схемах.
Редактор не меняет surfaces/exhibits/doors базового Room. Accent меняет отделку стен на клиенте,
не геометрию и не подписи/авторство картин. Runtime guide placements полностью заменяют
базовое положение/rotation_y при render, targeting, ask, action и distance/LOS на сервере.
Все другие методы используют тот же effective-world порт, а не прямой обход в файловый каталог.

Дефолт C01 для каждого зала 12×12: accent `#D9D2C3`, neutral, исходные guide placements,
slots a=(3,0,4), b=(9,0,4), один светильник `lamp_01` на a, yaw=0, head_pitch=0,
on=true, installation_visible=false, npc_count=10. Учебная составная установка —
поворотный стенд «Цвет и свет» из основания и двух цветных створок, в (6,0,3),
габариты 1×1.5×0.5 м; её покачивание/вращение створок декоративное на клиенте.
Это отдельный объект, не ящик и не дополнительное взаимодействие с крышкой.
Для других валидных миров сервер обязан проверить эти позиции/геометрию до активации
расширения; если не подходят — требуется подготовленный seed, startup завершается ошибкой.

Все позиции на полу (y=0), внутри bounds с запасом 0.5 м, без пересечения collidable surfaces.
Slots/установка должны быть не ближе 1 м к door/spawn/guide и друг другу; используется
геометрия текущего мира. Перемещение гида также не перекрывает эти места.
Дополнительные предметы, гиды и NPC не добавляют физических препятствий игрокам.
Светильник состоит из основания, стойки и поворотной головки: yaw∈[-π,π), head_pitch∈[-π/3,π/3].
Направление света при нуле — -Z с наклоном вниз π/4; head_pitch прибавляется к этому наклону.
SpotLight: цвет warm #FFD6A0 / neutral #FFFFFF / cool #C5DFFF, intensity=3,
distance=8, angle=π/6, penumbra=0.5, decay=2, shadows=false; глобальный свет сцены сохраняется.
`lighting` определяет цвет SpotLight и оттенок ambient; включение/выключение относится к лампе.
При переносе модель крепится к игроку: локально справа .35 м и вверх 1 м от точки пола,
направление следует yaw игрока; сохранённые углы используются после установки.

Runtime полон и ограничен **32 КиБ UTF-8 на payload**, NPC snapshot — 24 КиБ.
Входящие WS ≤16 КиБ, серверное сообщение ≤256 КиБ и очередь 1 МиБ сохраняются.
Новые объекты — только локальные примитивы; сетевые runtime/NPC события, как остальные
сетевые события, не входят в файловый числитель/знаменатель 10%. Дополнительные файлы
не загружаются; JSON/asset/photo reservations, один зал и освобождение GPU остаются обязательны.
Админские профили не кешировать в игровом AssetBudget и не включать в размер мира.
Не раздувать total_content_bytes примитивами или служебными данными.

## 3. Администратор и HTTP

Существующие аккаунты по умолчанию не admin. В PostgreSQL сохраняется admin membership.
Отдельная команда `./bin/admin grant --username NAME` назначает admin существующему
аккаунту после отдельной миграции; повтор безопасен, неизвестный username — ненулевой exit.
Команда использует DATABASE_URL, не печатает секреты и не создаёт пользователей/схему.
Новый `cmd/admin` и binary включить в make build, Docker и offline kit.
Не принимать роль от клиента. Отдельных паролей/токенов/API регистрации admin нет.

Все `/admin/*` требуют действующую сессию и роль на **каждом запросе**: 401 без сессии,
403 FORBIDDEN без роли. GET не требует игрового WS. PUT требует точный Origin как POST.
Размер PUT admin ≤65536 байт — явное исключение из обычных 16 КиБ. Только JSON UTF-8,
Content-Type application/json, неизвестные/повторные ключи/null запрещены, кроме явно nullable полей.
Все успешные/ошибочные ответы no-store/X-Request-ID. Все PUT admin суммарно 10/10 с/user,
превышение 429 RATE_LIMITED + retry_after_ms/Retry-After, GET clients polling ≤1/2 с на UI.

| Метод | Путь | Ответ 200 |
|---|---|---|
| GET | /admin/me | `{user_id,role:"admin"}` |
| GET | /admin/clients | `{clients: ClientMetric[]}` не более 32 |
| GET | /admin/rooms | `{rooms:[{room_id,title,revision}]}` все 24 C01 |
| GET | /admin/rooms/{room_id} | RoomRuntime |
| PUT | /admin/rooms/{room_id} | RoomRuntime; тело `{world_version,expected_revision,config}` |
| GET | /admin/guides | `{guides:[{guide_id,display_name,revision}]}` |
| GET | /admin/guides/{guide_id} | AdminGuide |
| PUT | /admin/guides/{guide_id} | AdminGuide; тело `{world_version,expected_revision,settings}` |

Комнаты/гиды только существующие в текущем каталоге, неизвестный ID →404 NOT_FOUND.
Неверная версия →409 WORLD_VERSION_MISMATCH; проигранный CAS →409 REVISION_CONFLICT,
никакой частичной записи. UI перечитывает, показывает конфликт, не затирает чужое изменение.
При ошибке SQL →503 SERVICE_UNAVAILABLE, никакого успешного broadcast до commit.
После неопределённого COMMIT нельзя подставлять старый overlay: затронутые соединения
закрыть 1011, восстановить состояние из БД; HTTP отдаёт 503, UI перечитывает.
Room PUT меняет config, сохраняет лампу на прежнем slot/её углы; если лампа удерживается,
отклоняет всю правку 409 OBJECT_BUSY. Если новый config делает slot текущей лампы невалидным,
правка отклоняется. Изменение runtime сериализовано с командами игроков через CAS.
После commit полный world.runtime всем owning WS этого зала, включая ещё not-ready.
Не держать game mutex на SQL/LLM. Reconnect читает durable состояние, даже при потере broadcast.

GuideSettings: display_name 1–64, subtitle 1–200, personality 1–2000, style/topic 1–1000,
constraints 1–20 строк до1000; сумма personality/style/topic/constraints ≤4000 кодовых точек.
Текст Unicode trim, без U+0000; фиксированные ограничения безопасности/русского языка и
обозначение учебной реконструкции не редактируются. material_ids — уникальный список 0–100
существующих материалов **этого** файлового профиля. Админ выбирает доступные знания,
не загружает файлы/URL и не редактирует тексты материалов в MVP.
AdminGuide содержит available_materials с id/excerpt≤200/exhibit_ids (только администратору).
До первого override revision=1: имя/subtitle из C01, инструкции из файлового профиля,
material_ids — все его материалы. При неоднозначных имени/subtitle одной личности
в разных залах seed отклоняется при startup.
Профиль общий для личности во всех залах; память user_id+guide_id сохраняется и не очищается.

Profile override хранится по `(world_version,guide_id)`, revision с 1. На **старте running**
worker один раз фиксирует effective profile+revision: queued возьмёт последние настройки,
running заканчивает со снимком прежних. B08-context/16000 codepoints/одна модель/очередь
и атомарная terminal+memory не меняются. Не отдавать приватные prompts/диалоги в admin API.
Смена имени/subtitle повышает revision всех затронутых комнат и рассылает world.runtime
с новым публичным именем атомарно с profile update; полный профиль игрокам не передаётся.

## 4. Светильник: object.act

Один lamp_01 на зал, два места a/b. Команды содержат movement_epoch и expected_revision
текущего runtime. Все требуют owning WS, ready, текущий epoch; старый epoch →STALE_MOVEMENT_EPOCH.
Объект не из текущего зала →NOT_FOUND; расстояние XZ ≤3 м и LOS от камеры обязательны.
Для take/aim/power цель — slot; для place — выбранный slot. Held-операции разрешены
только владельцу; чужой владелец →OBJECT_BUSY (без передачи ownership). Максимум один
переносимый предмет у игрока. Лампа не переносится между залами.

| action | Дополнительные поля payload | Правило |
|---|---|---|
| take | нет | Лампа должна стоять; holder_user_id становится self |
| place | slot_id=a\|b | Только владелец; целевой slot свободен, вернуть holder=null |
| aim | yaw,head_pitch | Только установленная лампа; held →OBJECT_BUSY |
| power | on:boolean | Только установленная лампа; held →OBJECT_BUSY |

Общие поля `{object_id:"lamp_01",movement_epoch,expected_revision,action}`.
Повтор обычного UUID в соединении →DUPLICATE_REQUEST, как у inspect. Между соединениями
нет отдельной durable idempotency; CAS+полный снимок исключают повтор неизвестного результата.
Каждая успешная команда, включая установку прежних углов/on, повышает revision на 1.
Ответ `object.acted {action,runtime}` отправителю с request_id, затем world.runtime
остальным в зале без request_id; отправитель уже применил тот же полный runtime.
При конфликте error REVISION_CONFLICT без изменения. Проверка ownership/ready/epoch
повторяется перед commit с connection ID, поздняя команда старого socket не меняет новый.
На disconnect/replacement/logout/door/shutdown лампа атомарно возвращается на последний
slot, holder=null; только после успешного release подтверждать door. Последний slot
резервируется за лампой при переносе. На startup убрать все stale holders до listener.
Ошибка release не должна оставлять молча потерянное владение: закрыть 1011;
сервер повторяет release с backoff 1/2/5 с (далее каждые 5 с до успеха/shutdown),
а перед следующим take/attach комнаты делает lazy CAS-release владельца, чей
connection ID уже отсутствует. Cleanup всегда сравнивает сохранённый connection ID,
не освобождая лампу нового владельца. Неизвестный исход COMMIT разрешается перечитыванием.
До release подтверждения камера перемещаться по залу может; дверь временно заблокирована.
После release конфликта ревизий перечитать и повторить cleanup только для того же owner/connection.
В БД хранить holder connection ID, но **не отдавать его** клиентам.

## 5. Массовые NPC и анимации

10 посетителей в каждом активном C01 зале, админ может уменьшить npc_count до 0.
NPC — простые люди из головы, туловища, двух рук и двух ног. FSM без Ollama:
walking → idle при игроке ближе 1 м; talking при принятом chat.send с непустым текстом,
если отправитель того же зала ≤3 м; повернуться к нему на 3 с, затем walking.
Повтор разговора продлевает 3 с; выбирается последний отправитель, при равном времени
минимальный user_id. Фото без текста не триггерит. Дистанции — XZ.
Маршруты детерминированы world_version+room_id+NPC index, проходят только валидные точки
и отрезки существующей геометрии; NPC не проходят стены и двери и не меняют зал.
Скорость 0.6 м/с. Talking приоритетнее idle; idle/talking передают speed_mps=0. Простой обход: при близости игрока остановиться, сложный crowd/pathfinding не нужен.
Маршруты подготавливаются до listener: ограниченная сетка до 64×64 точек, проверка
цилиндра радиусом 0.3 м и полных отрезков, исключение XZ-области каждой двери
радиусом door.radius+0.3 м. Если безопасного отрезка нет, NPC остаётся idle в валидной
точке; отсутствие валидной точки запрещает startup с указанием зала.
Во время talking NPC смотрит на актуальную позицию отправителя; после его ухода
сохраняет последнее направление до истечения 3 с. Затем снова проверяет близость игроков.
Сервер FSM tick 5 Гц только для залов с owning WS; пустой зал освобождается и при входе
создаётся заново. Позиции NPC не пишутся в SQL. room_instance_id меняется при каждом создании
симуляции; seq начинается с 1, клиент принимает новую instance после смены зала/первого snapshot,
внутри неё только растущий seq. При изменении npc_count отправляется полный список;
отсутствующие ID удаляются. Снимки всем owning WS зала после runtime; с нулевым count — [].
NPC IDs npc_00..npc_09, state walking|idle|talking, position, yaw, speed_mps, phase [0,2π).
Фронт интерполирует 200 мс, процедурно качает конечности и поворачивает голову;
сервер не передаёт кости. Гиды также составные: idle покачивание и жест во время guide.started
до terminal, без новых сетевых событий. Общие геометрии/материалы, InstancedMesh для NPC,
dispose на смене зала, без отдельных текстур/имён над каждым NPC и теней от каждого NPC.

## 6. Просьбы к гиду: guide.action

Отдельная кнопка «Изменить экспозицию» и отдельная команда, не скрытый side effect guide.ask.
Payload `{guide_id,text,movement_epoch,expected_revision}`; text 1–200 Unicode после trim,
без NUL. Owning/ready/epoch/дистанция ≤3/LOS как guide.ask, effective placement обязателен.
Локальный классификатор: Unicode lower+trim, сжать пробелы, убрать завершающие .!?;
распознаёт **только** точные фразы таблицы (без LLM/интернета):

| Фразы | effect |
|---|---|
| покажи макет; добавь макет; покажи учебный макет | show_installation |
| убери макет; скрой макет | hide_installation |
| сделай освещение теплее; тёплый свет | warm_light |
| сделай освещение холоднее; холодный свет | cool_light |

Неизвестная просьба →error UNSUPPORTED_ACTION, без генерации и изменения мира.
Установка — описанный выше стенд «Цвет и свет», один на зал; повтор show не создаёт дубль.
Warm/cool меняет config.lighting (и цвет установленной лампы) без автосоздания предметов.
Изменение использует ту же SQL/CAS-room операцию, что admin и object.act; сохраняется до ответа.
Ответ `guide.action.completed {guide_id,effect,runtime}` только отправителю с request_id,
world.runtime остальным в зале. Каждое принятое действие повышает revision, даже если уже применено.
Обычная per-connection UUID дедупликация; не создаёт generation, новую memory event или LLM summary.
Личная память диалога B08 продолжает работать отдельно. Обычные guide.ask/очередь не блокируются.

## 7. Только FPS и ping

`client.metrics` без request_id: `{fps:number|null,visible:boolean}` раз в 2 с.
fps — среднее rAF-кадров за фактические последние 2 с, конечное 0..1000; visible=false
требует fps=null. Клиентский FPS — заявленный браузером, не защищённый benchmark.
При visible=true значение null также допустимо, если измерение ещё недоступно.
Скрытая вкладка отправляет visible=false сразу и не генерирует фиктивные FPS=0.

`telemetry.probe {nonce}` сервер → текущий socket раз в 5 с после snapshot.
`telemetry.pong {nonce}` клиент → сервер сразу, без request_id. Сервер измеряет RTT своим
монотонным clock, принимает только единственный outstanding nonce данного connection ID,
после 5 с без ответа ping становится null. Не принимать присланные клиентом milliseconds.
Фоновая вкладка может иметь повышенный RTT; это не ping LLM/БД и не WebSocket protocol ping.
Probe не заменяет уже существующий transport ping/pong и его timeout.

Metrics/pong допускаются до ready и исключены из UUID-дедупликации, лимита 10000 и общего
30/10с; отдельный предел каждого типа 2/с/connection. Лишние валидные telemetry сообщения
отбрасываются без error/broadcast; некорректная структура даёт обычный VALIDATION_ERROR,
не обновляет метрики. Исключение применяется только после аутентификации/Origin.
Распознанные telemetry-сообщения с неверным payload также не расходуют обычный
command rate/UUID; неразбираемый JSON и неоднозначные повторные ключи следуют общим
правилам ошибок транспорта. sampled_at меняется только у принятого metrics,
не у отброшенного по частоте или невалидного сообщения.
Данные хранятся в RAM по connection ID; replacement сбрасывает измерения, старый callback
не переписывает новые. disconnect немедленно удаляет строку. Нет истории, SQL, новых метрик.
Admin poll GET /admin/clients раз в 2 с: user_id,display_name,room_id,fps,ping_ms,
visible,sampled_at nullable,stale. FPS протухает через 6 с →null, stale=true; sampled_at —
время последнего валидного metrics. Ping отдельно null после 5 с. Начальные значения null,
visible=false,stale=true. Не выдавать cookie/session ID/IP/prompt/dialogue.
Границы stale и timeout включительные: возраст metrics >=6 с и outstanding probe
>=5 с. Первый probe планируется через 5 с после attach, следующие через 5 с;
его постановка в очередь выполняется существующим игровым tick (100 мс), без I/O
под mutex. После ответа nonce погашается; прежний ping сохраняется до timeout
следующего неотвеченного probe. Фоновая вкладка со свежим metrics имеет stale=false,
fps=null; stale не означает hidden. UI polling раз в 2 с реализуется отдельно на frontend.
RTT фиксируется по времени получения pong до SQL-проверки сессии; изменение публичных
данных выполняется только после её успеха и повторной проверки connection ID.

## 8. Лимиты, ошибки и интеграционная приёмка

Новые обычные команды room.sync/object.act/guide.action входят в 30/10с и 10000 UUID.
Дополнительно object.act ≤10/10с/user, guide.action ≤3/10с/user; не сбрасывать reconnect.
room.sync ≤2/10с/user. Превышение →RATE_LIMITED с retry_after_ms.
Новые коды: REVISION_CONFLICT, OBJECT_BUSY, UNSUPPORTED_ACTION. HTTP 409 для первых двух;
UNSUPPORTED_ACTION только WS. Существующие коды сохраняются. Порядок проверок обычных
команд: общий rate/структура/dedup → owning/ready/epoch → объект/дистанция/LOS →
revision/владение → commit. room.sync требует owning, но не ready и не меняет состояние.
Обычный chat/cancel остаётся доступен до ready.

Демонстрация: admin меняет оформление/личность → два браузера видят результат; FPS+ping
обоих видны; один игрок берёт лампу, второй получает OBJECT_BUSY; первый ставит и
поворачивает головку, все видят свет; 10 посетителей двигаются/останавливаются/реагируют
на чат; просьба гиду показывает стенд/меняет освещение; reconnect/restart восстанавливает
room/profile/lamp без stale holder. Затем LAN без WAN и localhost с физически выключенным
Wi-Fi. Все файлы/модели локальные, 10% соблюдается на переходах/фото.

Машинные схемы задают структуру; геометрия, лимиты байтов/сумм, conditional state,
CAS, атомарность и порядок сообщений проверяются реализацией и тестами по этому документу.
