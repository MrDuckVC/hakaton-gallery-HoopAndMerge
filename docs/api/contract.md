# API v1 — виртуальная галерея

Нормативный контракт фронтенда и бэкенда. Имеет приоритет над сетевыми примерами в `plan.md` и `frontend-plan.md`. Старые маршруты и события не поддерживаются.

Объём v1: аккаунты, один загруженный зал, переходы через двери, игроки, общий чат, гиды с личной историей, фотографии и альбом. Мини-карта, задания, личные сообщения, модели и предзагрузка соседних залов не входят в v1.

## 1. Общие правила

- HTTP: `/api/v1`; WebSocket: `/api/v1/ws`. Один origin; прокси разработки для `/api` поддерживает WS upgrade.
- JSON UTF-8, `snake_case`. Успешный ответ — непосредственно объект; `204` без тела. Изображения и multipart — явно указанные исключения.
- ID — непрозрачная непустая строка до 128 ASCII-символов. В URL кодируется как отдельный сегмент. Клиент не выводит из ID другие значения.
- Время — UTC RFC 3339. Размеры — целые байты, 1 МиБ = 1 048 576 байт. Числа конечные; целые числа не превышают `2^53−1`.
- В схемах ниже `?` означает необязательное поле, `T|null` — обязательное поле с допустимым `null`. Остальные поля обязательны. Необязательные поля запроса опускаются; `null` в них не принимается.
- Неизвестные поля запросов отклоняются; неизвестные поля ответов клиент игнорирует. Неизвестное серверное WS-событие игнорируется с записью в диагностический журнал.
- Длина текста считается в Unicode-кодовых точках. Пользовательские текстовые поля, кроме пароля, обрезаются по краям по Unicode White_Space. HTML не интерпретируется. Отображение только как текст.
- Обычный HTTP JSON-запрос — не более 16 КиБ; клиентское WS-сообщение — не более 16 КиБ. Лимит задаётся на полный декодированный текст сообщения.
- Все HTTP-ответы имеют `Cache-Control: no-store`. Все маршруты, кроме register/login, требуют сессию.

### Общие типы

```ts
type Vec3 = { x: number; y: number; z: number };
type Rotation = { yaw: number; pitch: number };
type Pose = { room_id: string; position: Vec3; rotation: Rotation };
type User = { id: string; username: string; display_name: string; avatar_color: string };
type Player = {
  user_id: string; display_name: string; avatar_color: string;
  room_id: string; position: Vec3; rotation: Rotation;
  movement_epoch: number; ack_seq: number;
};
type ErrorBody = {
  code: string; message: string;
  fields?: Record<string, string>;
  retry_after_ms?: number;
};
```

`avatar_color` и цвета поверхностей — `#RRGGBB`. Координаты глобальные, метры, правая система, Y вверх. Положение игрока — точка на полу; все полы v1 имеют Y = 0, прыжков нет. Камера выше позиции на 1,65 м. Игрок — вертикальный цилиндр радиусом 0,3 м и высотой 1,8 м.

Взгляд при нулевых углах направлен вдоль −Z. `yaw` — вокруг +Y по правилу правой руки, диапазон `[−π, π)`; `pitch` положителен вверх, диапазон `[−π/2, π/2]`. Направление взгляда: `(-sin(yaw)*cos(pitch), sin(pitch), -cos(yaw)*cos(pitch))`.

### Ошибки

HTTP: `{ "error": { "code": "VALIDATION_ERROR", "message": "Некорректные данные", "request_id": "server-generated-id" } }`. Внутри `error` — `ErrorBody` и обязательный серверный `request_id`. Он также возвращается в `X-Request-ID` каждого HTTP-ответа.

| HTTP | code | Условие |
|---|---|---|
| 400 | `INVALID_JSON`, `VALIDATION_ERROR`, `INVALID_CURSOR` | Некорректный запрос |
| 401 | `UNAUTHENTICATED`, `INVALID_CREDENTIALS` | Нет сессии / неверный вход |
| 403 | `FORBIDDEN`, `ROOM_NOT_ACCESSIBLE`, `OUT_OF_RANGE` | Origin / доступ / расстояние |
| 404 | `NOT_FOUND` | Нет объекта или он приватен для другого пользователя |
| 409 | `USERNAME_TAKEN`, `WORLD_VERSION_MISMATCH`, `GAME_NOT_READY`, `IDEMPOTENCY_CONFLICT` | Конфликт состояния |
| 413 | `PAYLOAD_TOO_LARGE` | Превышен размер |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Неподдерживаемый формат |
| 429 | `RATE_LIMITED` | Превышена частота |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка без технических подробностей |
| 503 | `SERVICE_UNAVAILABLE` | Хранилище или сервер временно недоступны |

Для 429 обязательны `retry_after_ms` и HTTP `Retry-After` в секундах с округлением вверх. HTTP-коды не передаются внутри WS; там используются строковые `code`.

## 2. Авторизация и восстановление

| Метод и путь | Запрос | Успешный ответ |
|---|---|---|
| `POST /auth/register` | `{username, display_name, password}` | `201 {user: User}` |
| `POST /auth/login` | `{username, password}` | `200 {user: User}` |
| `POST /auth/logout` | Без тела | `204` |
| `GET /me` | — | `200 {user: User, player_state: Pose}` |

- `username`: `[A-Za-z0-9_]{3,32}`, хранится и возвращается в нижнем регистре, уникален без учёта регистра.
- `display_name`: 1–32 кодовые точки после trim; символ U+0000 запрещён → 400 `VALIDATION_ERROR`. Пароль этим запретом не ограничивается.
- `password`: 8–128 байт UTF-8; без trim и нормализации.
- Register/login создают новую сессию, заменяют и отзывают прежнюю сессию из cookie, если она была действительна. Другие сессии аккаунта сохраняются.
- Cookie `museum_session`: случайный непрозрачный токен, `HttpOnly; SameSite=Lax; Path=/; Max-Age=86400`. `Secure` при HTTPS; отключение разрешено только явной конфигурацией локального HTTP-запуска. Срок 24 часа без продления. В БД хранится хеш токена.
- Для всех POST, включая login/register, и WS upgrade проверяется точное совпадение Origin с настроенным списком. Отсутствующий Origin и `null` отклоняются. CORS для сторонних origin не включается.
- Logout идемпотентен: даже без действующей сессии удаляет cookie и возвращает 204; действующую отзывает и закрывает её WS. Проверка Origin сохраняется.
- Новый пользователь получает стартовый зал и безопасную spawn-позицию. Если сохранённый зал/позиция недопустимы для текущего мира, сервер сохраняет исправленную стартовую позицию.
- `/me` — предварительное состояние. После подключения окончательным является `world.snapshot`.
- Позиция сохраняется раз в 5 секунд и при штатном отключении; переход — до подтверждения. Аварийное завершение может потерять последние 5 секунд перемещения. Ошибка периодического сохранения закрывает игровое соединение с 1011; молча продолжать несохраняемую игру нельзя.

## 3. Мир, ресурсы и бюджет

| Метод и путь | Ответ |
|---|---|
| `GET /world/manifest` | `Manifest` |
| `GET /world/rooms/{room_id}?version={world_version}` | `Room` |
| `GET /world/assets/{asset_id}?version={world_version}` | JPEG/WebP |

`version` обязателен. Другая версия → 409 `WORLD_VERSION_MISMATCH`. Версия неизменна до рестарта; любые изменения описаний/изображений требуют новой версии. Манифест доступен любой действующей сессии. Доступ к описанию и ресурсам имеет только текущая игровая сессия с активным WS, только для текущего зала. Asset разрешён, если входит в его пакет. Проверка выполняется при начале HTTP-запроса; начатый ответ может завершиться после перехода, клиент обязан отбросить устаревшие данные.

```ts
type Manifest = {
  world_id: string; world_version: string;
  total_content_bytes: number; client_cache_limit_bytes: number;
  max_loaded_rooms: 1; photo_reserve_bytes: 3145728;
  movement: {
    send_rate_hz: 10; state_rate_hz: 10; max_speed_mps: 4;
    player_radius_m: 0.3; player_height_m: 1.8; camera_height_m: 1.65;
  };
};
type RoomPackage = {
  room_id: string; descriptor_bytes: number;
  assets: { id: string; bytes: number; content_type: "image/jpeg"|"image/webp" }[];
};
type Room = {
  id: string; world_version: string; title: string;
  bounds: { min: Vec3; max: Vec3 };
  surfaces: {
    id: string; position: Vec3; size: Vec3;
    color: string; collidable: boolean;
  }[];
  doors: {
    id: string; target_room_id: string; label: string;
    position: Vec3; interaction_radius_m: 1.5;
  }[];
  exhibits: {
    id: string; title: string; description: string;
    image_asset_id: string; position: Vec3; rotation_y: number;
    width_m: number; height_m: number; interaction_radius_m: 3;
  }[];
  guides: {
    id: string; display_name: string; subtitle: string;
    position: Vec3; rotation_y: number; interaction_radius_m: 3;
  }[];
};
```

`surfaces` — блоки без вращения; `position` — центр, `size` — положительные размеры. `bounds` ограничивает весь объём зала. Экспонат — плоскость с центром `position`, лицом к +Z при `rotation_y=0`. Экспонаты и гиды сами по себе не блокируют движение; препятствия задаются поверхностями. Для пола касание нижней границы цилиндра разрешено; проникновение в блоки запрещено.

Дверь — точка взаимодействия на доступной стороне стены. Через стену нельзя пройти обычным движением; переход выполняется отдельной командой. Серверный контент задаёт безопасную spawn-позицию для каждой направленной двери. Каждый зал имеет выход, каждый target существует. Для v1 не требуется загружать геометрию соседей.

`guide.id` обозначает личность, общую для нескольких залов; в одном зале не более одного экземпляра данной личности. Память общая по паре пользователь + личность. ID экспонатов и дверей глобально уникальны в версии мира.

### Учёт бюджета

- `total_content_bytes` — сумма размеров уникальных файлов всех описаний залов и изображений до HTTP-сжатия. Манифест и сетевые события в знаменатель не входят. Фото пользователей знаменатель не увеличивают.
- `client_cache_limit_bytes = floor(total_content_bytes / 10)`.
- Числитель: размеры удерживаемых файлов мира, их резервов загрузки, клиентских JPEG/WebP фото и резервов фото. Общий asset считается один раз. RAM/GPU после декодирования — отдельная метрика, не этот счётчик.
- Размеры описаний — точные UTF-8 байты отдаваемого JSON. JSON отдаётся из подготовленного файла без динамического переформатирования. Списки assets уникальны и включают все зависимости зала.
- При подготовке контента каждый пакет проверяется: `descriptor_bytes + sum(assets.bytes) + photo_reserve_bytes <= client_cache_limit_bytes`. Несоответствие блокирует запуск мира.
- До загрузки резервируются объявленные размеры. Резерв заменяется фактическим размером без двойного счёта. При превышении объявленного размера загрузка прекращается, результат удаляется, UI показывает ошибку контента.
- Разрешён один зал. При смене зала клиент отменяет загрузки, освобождает файлы, bitmap, текстуры, геометрию и материалы старого зала; только затем начинает новые загрузки. Резерв отменённой загрузки освобождается после прекращения чтения и удаления буферов.
- Фото используют не более 3 МиБ: один оригинал до 2 МиБ и до шести миниатюр по 128 КиБ. Перед новой съёмкой/открытием оригинала предыдущий оригинал освобождается. История чата хранит метаданные, изображения вне этих лимитов не подгружает.
- Постоянный кеш, Service Worker и `THREE.Cache` для контента не используются. `no-store` не заменяет освобождение клиентских объектов.

Это определение 10% — правило проекта; соответствие внешним условиям конкурса требует отдельного согласования.

## 4. WebSocket и соединение

Только текстовые JSON-сообщения. Успешному upgrade предшествуют проверки сессии и Origin; ошибки до upgrade — обычные HTTP. Бинарное сообщение закрывает WS с 1003, слишком большое — с 1009.

```ts
type ClientEnvelope = { type: string; request_id?: string; payload: object };
type ServerEnvelope = {
  type: string; event_id: string; server_time: string;
  request_id?: string; payload: object;
};
```

`request_id` обязателен у всех команд, кроме `player.move`; у move его нет. Это UUID v4, уникальный для команды. В одном соединении сервер помнит ID обычных команд до закрытия: повтор → `DUPLICATE_REQUEST`, без повторного действия. Не более 10 000 таких команд на соединение; после достижения лимита сервер закрывает его с 1012. Незавершённая генерация отменяется по общему правилу отключения. `guide.ask` имеет отдельную устойчивую идемпотентность (§7).

`event_id` уникален для события; служит дедупликации, не курсором восстановления. Сервер доставляет события по одному WS в порядке формирования. Ответ отправителю содержит исходный `request_id`; рассылки другим игрокам и спонтанные события — без него. Исключение: события генерации всегда коррелируются с исходным `guide.ask`.

Ошибка команды: событие `error`, payload `ErrorBody`. Если ID нельзя прочитать или его не было, `request_id` отсутствует. Неизвестный type → `UNKNOWN_EVENT`; неверный JSON → `INVALID_JSON`; неверные поля → `VALIDATION_ERROR`. Ошибки бизнес-правил WS используют также `GUIDE_BUSY`, `GUIDE_QUEUE_FULL`, `STALE_MOVEMENT_EPOCH`, `DUPLICATE_REQUEST`, `IDEMPOTENCY_CONFLICT`, `GAME_NOT_READY`, `OUT_OF_RANGE`, `NOT_FOUND`. При заполненной очереди обязателен retry_after_ms. Неверное перемещение дополнительно корректируется ближайшим `players.state`.

### Snapshot и присутствие

Первое сообщение после upgrade — `world.snapshot`; никакие другие события не опережают его.

```ts
// world.snapshot — только подключившемуся
{
  protocol_version: 1,
  world_version: string,
  self: Player,
  players: Player[],
  current_room: RoomPackage
}
// player.joined — остальным
{ player: Player }
// player.left — остальным
{ user_id: string }
// players.state — всем, 10 Гц
{ players: Player[] }
```

`world.snapshot.players` содержит всех остальных. `players.state.players` — полный список всех подключённых игроков, включая получателя; отсутствующих удаляют. Все записи содержат имя и цвет, так что состояние самодостаточно. Клиент показывает только игроков своего загруженного зала.

Начальные `movement_epoch=1`, `ack_seq=0`. Snapshot формируется согласованно с последующими событиями; соединение ещё не принимает движение до `world.ready`.

Одно игровое WS на аккаунт. Новое соединение атомарно заменяет старое, отменяя его генерацию; старое получает 4009. Поздние обработчики старого соединения не меняют состояние нового. Другим игрокам замена передаётся как `player.left`, затем `player.joined`.

| Close code | Значение | Клиент |
|---|---|---|
| 1000 | Штатное закрытие | Не переподключаться автоматически |
| 4001 | Сессия истекла/отозвана | Показать вход |
| 4009 | Подключён другой игровой клиент | Остановить повторы; предложить ручной вход в мир |
| 4006 | Неподдерживаемый протокол | Показать необходимость обновления клиента |
| 1003, 1008, 1009 | Формат/нарушение протокола | Остановить автоматические повторы |
| 1011, 1012, 1013, аномальный обрыв | Временная ошибка/рестарт/перегрузка | Переподключиться |

Сессия проверяется при upgrade, перед каждой изменяющей командой/фиксацией HTTP-запроса и отдельным таймером истечения; отзыв немедленно закрывает связанные WS.

Сервер отправляет WS ping каждые 20 секунд; без pong 10 секунд закрывает соединение. Браузер отвечает на протокольный ping автоматически. При временном обрыве клиент блокирует движение и команды; задержки повторов 1, 2, 4, 8, далее 10 секунд с jitter ±20%. Если upgrade не удался, клиент проверяет `/me`: 401 означает экран входа, сетевой сбой — повтор. При 4009 автоматические повторы запрещены.

После подключения клиент получает manifest, сверяет `world_version` со snapshot, освобождает прежний мир и загружает `current_room`. При расхождении версий закрывает WS и заново выполняет вход в мир. Накопленные команды и движения не воспроизводятся.

## 5. Загрузка, переходы и движение

### Готовность

Клиент загружает описание и все assets текущего пакета, строит сцену, затем отправляет:

```ts
// C → S: world.ready
{ world_version: string; movement_epoch: number }
// S → C: world.ready — подтверждение
{ movement_epoch: number }
```

Сервер принимает только актуальные версию и epoch. Повторная готовность с новым request_id безопасна. До подтверждения клиент не отправляет движение, осмотр, вопросы или фото; сервер отклоняет такие действия с `GAME_NOT_READY`. Чат, история, альбом и отмена генерации доступны. Если загрузка не удалась, UI остаётся в экране загрузки с повтором; тайм-аута готовности нет.

### Переход

```ts
// C → S: world.enter
{ door_id: string; movement_epoch: number }
// S → C: world.entered
{ self: Player; current_room: RoomPackage }
```

1. Клиент блокирует движение и посылает `world.enter` только из готового состояния.
2. Сервер проверяет epoch, дверь текущего зала, расстояние по XZ ≤1,5 м и отсутствие стены на пути к двери. При ошибке состояние не меняется; клиент снимает блокировку.
3. Сервер отменяет незавершённый вопрос, сохраняет целевой зал и spawn-позицию, увеличивает epoch на 1, устанавливает `ack_seq=0` и состояние «не готов». При ошибке сохранения переход не выполняется.
4. Сервер отправляет `world.entered` до любых `players.state` с новой позицией этому клиенту. Доступ HTTP переключается на новый зал атомарно со сменой состояния.
5. Клиент выгружает прежний зал, загружает пакет назначения и выполняет `world.ready`. `seq` начинается с 1 для нового epoch.

Повторный `world.enter` до готовности → `GAME_NOT_READY`. Неактуальный epoch → `STALE_MOVEMENT_EPOCH`. При потере подтверждения клиент переподключается и получает фактическое положение через snapshot. Переходы обратимы через двери целевого зала; неудачная загрузка не выполняет автоматический откат серверной позиции.

### Движение

```ts
// C → S: player.move, без request_id
{ movement_epoch: number; seq: number; position: Vec3; rotation: Rotation }
```

- 10 сообщений/с; `seq` — положительное целое, строго возрастает внутри epoch. Пропуски разрешены. `seq <= ack_seq` игнорируется. Старый epoch игнорируется; будущий epoch → VALIDATION_ERROR без изменения состояния.
- `room_id` клиент не назначает. Обычное движение не меняет зал. Y позиции всегда 0.
- Сервер обрабатывает команды последовательно. Максимальное перемещение: `4 * min(dt, 0.25)` метра с численной погрешностью не более 0,000001 м; dt — серверное время от прошлого обработанного move текущего epoch. Время сбрасывается только при первом ready данного epoch; повторный ready не влияет на движение. Долгий простой не накапливает запас перемещения. Клиентская скорость — не более 4 м/с.
- Сервер проверяет весь путь цилиндра, а не только конечную точку: границы зала и collidable surfaces. Пересечение стены или превышение скорости отклоняет всё перемещение; сервер сохраняет предыдущую позицию. Допустимый поворот принимается независимо от отклонённой позиции.
- У структурно валидного обработанного move `ack_seq` обновляется и при отклонении позиции. Неверная структура не изменяет `ack_seq`; возвращается `error` без request_id.
- Клиент корректирует себя по `players.state`; удалённых игроков интерполирует. При смене epoch очищает буфер движения и интерполяции соответствующего игрока.

## 6. Общий чат и осмотр

```ts
// C → S: chat.send
{ text?: string; photo_id?: string }
// S → все: chat.message
{
  message_id: string;
  author: { user_id: string; display_name: string };
  text: string;
  photo: Photo|null;
}
// C → S: exhibit.inspect
{ exhibit_id: string }
// S → C: exhibit.inspected
{ exhibit_id: string; inspected_at: string }
```

Чат: после trim текст 1–500 символов, либо отсутствует при наличии фото. Пустая строка считается отсутствием. Нужны текст или photo_id. В ответе отсутствующий текст становится `""`. Отправителю возвращается исходный request_id. История общего чата не хранится; после обрыва пропущенные сообщения не восстанавливаются, автоматической повторной отправки нет.

Фото может публиковать только владелец. Сервер сохраняет `published=true` до рассылки; повторная публикация разрешена. Опубликованное фото доступно всем вошедшим пользователям, даже после исчезновения сообщения из чата. Публикация необратима в v1.

Осмотр: экспонат текущего зала, расстояние по XZ ≤3 м, нет стены между камерой и центром экспоната. Повторный осмотр обновляет время последнего осмотра без дублирования достижения. Ответ — после сохранения. События осмотра и фото хранятся по пользователю, доступны его гидам как личная память.

## 7. Гиды

```ts
type DialogMessage = {
  id: string; role: "user"|"assistant"; text: string; created_at: string;
};
type Generation = {
  id: string; request_id: string; guide_id: string; exhibit_id: string|null;
  status: "queued"|"running"|"completed"|"failed";
  user_message: DialogMessage;
  assistant_message: DialogMessage|null;
  error: { code: string; message: string; retryable: boolean }|null;
};
// C → S: guide.ask
{ guide_id: string; text: string; exhibit_id?: string }
// S → C: guide.accepted
{ generation: Generation }
// S → C: guide.started
{ generation_id: string }
// S → C: guide.delta
{ generation_id: string; index: number; text: string }
// S → C: guide.completed
{ generation: Generation }
// S → C: guide.failed
{ generation: Generation }
// C → S: guide.cancel
{ generation_id: string }
// S → C: guide.cancelled — ответ на команду отмены
{ generation: Generation }
```

### Приём и выполнение

- Текст 1–2000 символов после trim. Личность гида должна присутствовать в текущем зале; расстояние XZ ≤3 м, луч от камеры к точке на высоте 1,65 м над позицией гида не пересекает collidable стены. Если указан экспонат, он принадлежит текущему залу; подходить к нему повторно не требуется.
- Один незавершённый вопрос на пользователя → иначе `GUIDE_BUSY`. Одна активная генерация на сервер; очередь FIFO до 8 ожидающих → иначе `GUIDE_QUEUE_FULL`, `retry_after_ms=5000`.
- Вопрос и запись Generation сохраняются до `guide.accepted`. Очередь реализуется через эти сохранённые записи. До accepted ошибка приходит как `error`, без создания генерации.
- `guide.accepted` предшествует started/delta/терминальному событию. accepted содержит queued; started означает переход в running. UI показывает «Ожидание» или «Гид отвечает», без численной позиции очереди.
- Все события генерации до её завершения направляются только соединению, принявшему вопрос, с request_id исходного ask. Delta — добавочный текст; индексы 0,1,2… Повторный индекс игнорируется; пропуск означает необходимость восстановить итог через HTTP.
- Ответ ограничен 8000 кодовых точек. Ожидание в очереди не более 120 секунд, выполнение не более 90 секунд. Превышение → failed с `AI_TIMEOUT`; недоступность модели → `AI_UNAVAILABLE`; превышение длины → `AI_OUTPUT_LIMIT`.
- completed содержит окончательный текст, заменяющий все delta, и отправляется после атомарного сохранения ответа и status=completed. failed содержит error и assistant_message=null. Частичный ответ не сохраняется в историю и не используется как память.
- Терминальный статус неизменяем. При ошибке хранения завершения сервер не сообщает об успехе и закрывает WS с 1011. При восстановлении хранилища незавершённая запись переводится в failed `SERVER_RESTARTED` до допуска новых вопросов пользователя.
- Уход от гида внутри зала не отменяет запрос. Переход в другой зал, разрыв/замена WS и выход отменяют queued/running с `CANCELLED`. Отключённому клиенту событие не гарантируется; запись остаётся в истории.
- Личность, материалы и контекст собирает сервер. История и память изолированы по user_id + guide_id. Клиент не передаёт prompt, роль или историю.

### Отмена и идемпотентность

`guide.cancel` доступен только владельцу. Неизвестная/чужая генерация → `NOT_FOUND`. Если статус queued/running, сервер атомарно устанавливает failed `CANCELLED`, отправляет `guide.failed` с request_id вопроса, затем `guide.cancelled` с request_id отмены. Если генерация уже терминальна, возвращает только `guide.cancelled` с существующим состоянием. Гонку отмены и завершения выигрывает первая сохранённая терминальная операция. Повторная отмена с новым request_id безопасна.

`retryable=true` только для `AI_TIMEOUT`, `AI_UNAVAILABLE`, `SERVER_RESTARTED`. Для CANCELLED и AI_OUTPUT_LIMIT — false. Новый вопрос после ошибки — явное действие пользователя с новым UUID.

Для ask уникальна пара `(user_id, request_id)` в БД. Повтор того же нормализованного payload возвращает только `guide.accepted` с текущей Generation, без новой генерации и без воспроизведения потока; другой payload → `IDEMPOTENCY_CONFLICT`. Проверка существующего ключа выполняется до проверки расстояния и очереди. После reconnect автоматически повторять ask не нужно: используется HTTP-история.

### История и восстановление

`GET /guides/{guide_id}/generations?limit=20&before={cursor}` → `200 {items: Generation[], next_before: string|null}`.

История — только текущего пользователя, доступна без игрового WS и независимо от зала. Известная личность без истории возвращает пустой список; неизвестная — 404. limit от 1 до 50, по умолчанию 20. Без before — последние записи; внутри страницы от старых к новым. Порядок фиксирован по времени создания вопроса и ID; cursor указывает на записи строго старше первой в странице. Курсор привязан к пользователю и гиду; неверный → INVALID_CURSOR.

Queued/running записи могут менять статус, поэтому после обрыва клиент заново читает последнюю страницу. Для точного восстановления известного вопроса: `GET /guides/{guide_id}/generations/by-request/{request_id}` → `Generation` или 404. При рестарте сервера все незавершённые записи переводятся в failed `SERVER_RESTARTED` до начала обслуживания. Старый `/guides/{guide_id}/messages` в v1 не используется: один объект истории включает вопрос, ответ и результат генерации.

## 8. Фотографии

```ts
type Photo = {
  id: string; owner_id: string; caption: string;
  room_id: string; exhibit_id: string|null; published: boolean;
  image_url: string; image_bytes: number;
  thumbnail_url: string; thumbnail_bytes: number;
  width: number; height: number; created_at: string;
};
```

| Метод и путь | Результат |
|---|---|
| `POST /photos` | `201 Photo` |
| `GET /photos?limit=6&cursor={cursor}` | `200 {items: Photo[], next_cursor: string|null}` |
| `GET /photos/{photo_id}/image` | JPEG/WebP |
| `GET /photos/{photo_id}/thumbnail` | JPEG/WebP |

POST — multipart, ровно один файл `image`, обязательные строковые `room_id`, `movement_epoch` (десятичное целое), необязательные `caption`, `exhibit_id`. Caption до 200 символов; при отсутствии сохраняется `""`. Отсутствующий exhibit_id сохраняется как null. Неизвестные и повторяющиеся multipart-поля отклоняются.

Лимиты: файл до 2 МиБ; весь multipart до 2 МиБ + 64 КиБ; width 1–1920, height 1–1080. Только неподвижный JPEG/WebP, проверка декодированием. Сервер сохраняет проверенный оригинал и создаёт миниатюру с длинной стороной ≤320 px и размером ≤128 КиБ. URL относительные, под `/api/v1`; Content-Type соответствует проверенному формату, `X-Content-Type-Options: nosniff`. Поля bytes — точные размеры отдаваемых файлов.

Нужна готовая игровая сессия, владеющая активным WS. При фиксации загрузки сервер повторно проверяет, что room_id и epoch ещё актуальны; иначе `GAME_NOT_READY`. На время захвата и загрузки клиент блокирует движение и переходы. При указанном exhibit_id требуются те же расстояние и видимость, что для inspect. Сервер проверяет контекст снимка, но не доказывает содержание пикселей.

`Idempotency-Key: UUID v4` обязателен для POST. Уникальность по user_id + ключ; хранится вместе с фото. Повтор с тем же хешем файла и нормализованными полями возвращает существующее Photo с 200, даже если игрок уже ушёл; другой запрос → 409 IDEMPOTENCY_CONFLICT. Повторы одновременно сериализуются. Ключ не переиспользуется для нового снимка. После потери ответа клиент повторяет тот же запрос с тем же ключом, а не создаёт новый.

201 отправляется после сохранения оригинала, миниатюры, метаданных и события памяти. При ошибке частичные файлы удаляются; приватный объект без полностью сохранённых файлов не становится доступным.

Альбом содержит только собственные фото, от новых к старым по `(created_at, id)`. limit 1–6, по умолчанию 6. Курсор непрозрачный, привязан к владельцу; новые фото не сдвигают ранее выданные страницы. `next_cursor=null` означает конец. Приватные оригиналы и миниатюры доступны только владельцу; опубликованные — любому авторизованному пользователю. Чужое приватное или отсутствующее фото → 404. Альбом и чтение снимков не требуют игрового WS.

## 9. Лимиты и совместимость

Лимиты ниже — скользящее окно; состояние лимитов не сбрасывается переподключением. Для аутентифицированных действий ключ — user_id, для входа — IP. При превышении обычных лимитов действие не выполняется и возвращается RATE_LIMITED с retry_after_ms до ближайшего освобождения окна.

| Действие | Лимит |
|---|---|
| Login + register | 10 попыток / 60 с / IP |
| player.move | 20 / 1 с; лишние отбрасываются без ack |
| Все остальные WS-команды суммарно | 30 / 10 с |
| chat.send | 5 / 10 с |
| Новый guide.ask | 3 / 60 с плюс один незавершённый |
| POST photos | 6 / 60 с, включая повторы |

Нарушение частоты move в течение 5 последовательных секунд закрывает WS с 1008. Запросы гидов дополнительно ограничены очередью и тайм-аутами. Сервер допускает не более 32 одновременных игровых соединений; при заполнении новый аккаунт получает HTTP 503 до upgrade (замена своего соединения разрешена). Размер серверного текстового сообщения — до 256 КиБ; мир при подготовке проверяется на соответствие snapshot/room package этому пределу. При исчерпании исходящей очереди клиента в 1 МиБ сервер закрывает соединение с 1013, не накапливая неограниченный буфер.

Изменение имён, обязательных полей или семантики требует новой версии протокола. Добавление необязательных полей ответа совместимо. В v1 используются только события, перечисленные в этом документе; `world.rooms_available`, `welcome`, `move`, `players.snapshot`, `guide.queued`, `guide.done`, `/ws` и маршруты без `/api/v1` не поддерживаются.

## 10. Проверки перед интеграцией

1. Новый аккаунт → me → snapshot → manifest → пакет зала → ready → движение.
2. Два игрока: присутствие, полный players.state, общий чат; чужое приватное фото недоступно.
3. Переход при бюджете только на один зал: старый полностью выгружается; устаревшие move/HTTP-ответы не меняют новый мир.
4. Две вкладки: замена WS не запускает цикл переподключений; истёкшая сессия приводит к экрану входа.
5. Гид: очередь, поток, отмена одновременно с завершением, потеря accepted/completed, восстановление через историю без повторной генерации.
6. Фото: повтор POST после потери ответа не создаёт дубль; смена epoch во время загрузки отклоняется; публикация открывает доступ только после сохранения.
7. Рестарт: позиция восстанавливается, незавершённый вопрос имеет терминальный статус, новая версия мира очищает старый клиентский контент.
8. По всему маршруту загруженные байты + резервы не превышают manifest.client_cache_limit_bytes, включая фото и миниатюры.
