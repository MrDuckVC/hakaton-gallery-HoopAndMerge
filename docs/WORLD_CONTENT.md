# Подготовка локального мира B03

Сервер читает `WORLD_DIR/catalog.json` после проверки схемы PostgreSQL и до открытия HTTP listener. На проверку мира отводится до 60 секунд с отменой. Любая ошибка чтения, геометрии, ссылок, бюджета или snapshot блокирует запуск; отсутствующий мир не заменяется фиктивным spawn. Готовые материалы C01 включены в `content/world`; версия `gallery_c01_v1`. Экскурсия, происхождение, бюджет и обновление — [content/README.md](content/README.md).

## Серверный индекс

Все поля обязательны. `rooms`, `assets`, `profiles` — массивы `{ "id": "...", "file": "relative/path" }`; пустой profiles допустим для мира без гидов. `file` — путь относительно WORLD_DIR с `/`, без абсолютного пути, `.`/`..` и обратного слеша. Чтение через `os.Root` запрещает выход наружу через symlink. Файлы должны быть обычными: тип проверяется до открытия и по реально открытому дескриптору. На Unix используется O_NONBLOCK, чтобы FIFO, в том числе подменённый между stat и open, не блокировал startup и отмену. HTTP никогда не преобразует переданный ID в файловый путь. При подготовке мира room/asset IDs с сегментами `.`/`..` отклоняются, чтобы каждый принятый ресурс был доступен через безопасный HTTP URL; остальные ID остаются непрозрачными.

```json
{
  "world_id": "gallery",
  "world_version": "world_v1",
  "rooms": [
    {"id": "hall_a", "file": "rooms/a.json"},
    {"id": "hall_b", "file": "rooms/b.json"}
  ],
  "assets": [{"id": "painting_a", "file": "assets/a.webp"}],
  "profiles": [{"id": "guide_a", "file": "profiles/a.json"}],
  "start": {
    "room_id": "hall_a",
    "position": {"x": 2, "y": 0, "z": 2},
    "rotation": {"yaw": 0, "pitch": 0}
  },
  "spawns": {
    "door_a_b": {
      "room_id": "hall_b",
      "position": {"x": 2, "y": 0, "z": 2},
      "rotation": {"yaw": 0, "pitch": 0}
    },
    "door_b_a": {
      "room_id": "hall_a",
      "position": {"x": 2, "y": 0, "z": 2},
      "rotation": {"yaw": 0, "pitch": 0}
    }
  }
}
```

Это иллюстрация формата, не готовый мир: для запуска нужны файлы и достаточно реального контента для бюджета. Пример публичного описания — [api/examples/room.json](api/examples/room.json), схема — [api/contract.md](api/contract.md). Описание содержит тот же ID, что индекс, и `world_version`, равную версии индекса и WORLD_VERSION.

Profile — строго проверяемый серверный JSON личности B08; guide.id ссылается на ID записи profiles. Обязательные поля, пределы, материалы и демонстрационные профили описаны в [GUIDES.md](GUIDES.md). Профили, индекс и серверные spawns не выдаются клиентам и не увеличивают total_content_bytes.

JSON должен быть UTF-8 без повторяющихся ключей, lone surrogates, null вместо обязательного значения и хвостовых данных. Неизвестные поля индекса и Room отклоняются. Изображения проверяются декодированием, формат определяется байтами: только JPEG или статический WebP; расширение не задаёт MIME. WebP decoder — upstream [golang.org/x/image/webp v0.47.0](https://pkg.go.dev/golang.org/x/image@v0.47.0/webp), BSD-3-Clause; зависимости скачиваются до офлайн-запуска.

## Геометрия и ссылки

Проверяются конечные координаты, упорядоченные bounds с полом Y=0 и достаточным местом для цилиндра игрока, положительные размеры блоков/экспонатов, цвета #RRGGBB и радиусы взаимодействия из контракта. Декоративный объём пола и стен может пересекать границы bounds; сами безопасные позы должны вмещать цилиндр радиусом 0.3 м и высотой 1.8 м. Касание пола и препятствия допустимо, проникновение — нет.

Room IDs уникальны, door/exhibit IDs глобально уникальны, surface IDs уникальны внутри комнаты. Guide personality может встречаться в нескольких залах, внутри одного — один раз. Все ссылки на изображения и profiles разрешаются через индекс.

В каждом зале есть выход в другой существующий зал. Каждой направленной двери соответствует ровно один spawn в целевом зале. Старт, spawn и точка двери доступны цилиндру; углы соответствуют контракту. Граф переходов должен быть связным от старта в обоих направлениях: из любого зала можно вернуться. Идентичные парные door IDs не требуются.

## Байты, версии и выдача

Каждый файл комнаты и каждое используемое изображение учитывается однократно во всём мире. Повтор ссылки на asset в комнате не дублирует пакет. Неиспользуемые изображения не увеличивают знаменатель. Один файл регистрируется под одним публичным ID: повторная регистрация того же файла через hardlink/symlink под другим ID отклоняется, чтобы aliases не увеличивали бюджет и не создавали неоднозначные резервы. Для общего изображения используйте один asset ID во всех комнатах.

`client_cache_limit_bytes = floor(total_content_bytes / 10)`. Для каждой комнаты исходный JSON + уникальные изображения + 3145728 байт резерва фото должны помещаться в этот лимит. Нельзя добавлять пустые файлы или padding для увеличения знаменателя.

Отдельно проверяется консервативная верхняя граница полного world.snapshot: пакет, envelope и все 32 игрока с максимальными строками, JSON escaping и безопасными целыми. Предел — 262144 байт. Общие wire DTO и sizer находятся в inbound/worldwire; B04 должен использовать ту же форму snapshot.

Каталог сохраняет исходные байты в памяти. Объём RAM учитывайте при подготовке сервера: кроме самих файлов нужны структуры и временные буферы startup. HTTP выдаёт копии байтов с точным Content-Length; JSON не форматируется заново. Любые изменения файлов требуют новой WORLD_VERSION и рестарта; изменения на диске после проверки не меняют текущую выдачу.

GET manifest требует только действующую cookie-сессию. Rooms/assets дополнительно требуют единственный непустой `version`: неправильный формат → 400 VALIDATION_ERROR, другая версия → 409 WORLD_VERSION_MISMATCH. Активная owning WS-сессия и её текущий зал проверяются один раз до выдачи, даже если ready ещё не подтверждён. Не-владелец без активного игрового соединения получает GAME_NOT_READY; чужой зал/изображение — ROOM_NOT_ACCESSIBLE; отсутствующий объект — NOT_FOUND. После начала выдачи ответ может завершиться после перехода.

B04 подключает атомарный порт `Ownership.OwningRoom(ctx, sessionID, userID)`. В B03 production использует NoConnections и не разрешает пакеты по одному login или предварительному SQL-положению. Manifest, регистрация и восстановление позы уже используют настоящий каталог.

## Проверка поставляемой галереи C01

`make world-check` из корня проверяет готовые файлы через тот же Files → usecase/world → SnapshotSizer, который используется при startup, и печатает детерминированный JSON-отчёт. Он сравнивается с [content/budget.json](content/budget.json) в тестах. Каталог содержит 24 зала и три серверных профиля; полный источник и правила подготовки — [content/README.md](content/README.md).
