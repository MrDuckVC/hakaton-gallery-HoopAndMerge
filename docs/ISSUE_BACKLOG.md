# Задачи реализации MVP

Основание: REQUIREMENTS.md, api/contract.md и уточнения организатора от 31.10.2026. Список покрывает весь продукт; frontend-код остаётся в отдельном репозитории. Пока его адрес не указан, frontend issues ведутся в текущем репозитории как общий tracker.

Уже есть: Go-модуль, минимальная cmd/server, тест запуска, локальный порог покрытия 60%, GitHub Actions и Dockerfile каркаса. Это не готовые API/БД/игра. Эти работы повторно не планируются.

План на два дня — порядок приоритетов, не подтверждённая оценка длительности. Backend и frontend разрабатываются параллельно по контракту с fake ports/fixtures. Зависимости ниже обозначают точки интеграции; они не требуют ждать реального сервера для работы над клиентом. Финальный показ Q02 требует завершённых I01/A01/C01/Q01. В GitHub проверены 20 sub-issue связей с #1 и Blocked by у #21: #14, #12, #13, #20.

Первый день: B01–B08, A01, C01, I01, F01–F04 и промежуточный LAN/localhost-показ. Второй день: B09/B10/F05, доводка контента/памяти, Q01/Q02. При нехватке времени сокращается декор, а не обязательные правила/локальность/память/бюджет.

Родительская GitHub issue: https://github.com/MrDuckVC/hakaton-gallery-HoopAndMerge/issues/1 — объединяет 20 дочерних задач.

## B01. Backend. Реализовать запуск сервера, конфигурацию и миграции

GitHub: https://github.com/MrDuckVC/hakaton-gallery-HoopAndMerge/issues/2

**Требования:** R02 R07 R11. **Этап:** День 1.

### Цель

Превратить Go-каркас в запускаемый сервер с явным lifecycle и постоянным PostgreSQL.

### Что сделать

- [ ] Создать config и composition root cmd/server; HTTP_ADDR, DATABASE_URL, ALLOWED_ORIGINS, COOKIE_SECURE, WORLD_DIR/WORLD_VERSION, PHOTO_DIR, OLLAMA_BASE_URL/OLLAMA_MODEL, LOG_LEVEL; документировать в .env.example.
- [ ] Подключить закреплённый upstream pgx/v5, startup DB check и выбранный инструмент append-only миграций; подготовить users/sessions/player_states. Остальные таблицы добавляют задачи их подсистем.
- [ ] Настроить deadlines HTTP/DB, корректное завершение по сигналу, остановку новых соединений и порты lifecycle для сохранения позиций/отмены генераций. Не держать транзакции при сетевом I/O.
- [ ] Сохранить domain <- usecase <- adapters, проверить граф импортов; записать реальные команды запуска и миграций.

### Приёмка

- Сервер запускается с корректным env и останавливается по сигналу с deadline; некорректный config и недоступная БД дают понятную ошибку без секретов.
- Миграции применяются на отдельной тестовой БД; повторный запуск не очищает пользовательские данные.
- build/vet/tests/lint проходят, суммарное покрытие >=60%; domain/usecase не импортируют инфраструктуру.

### Не входит

Игровые сценарии, UI и раздача frontend dist — другие задачи.

## B02. Backend. Реализовать аккаунты, cookie-сессии и проверку Origin

GitHub: https://github.com/MrDuckVC/hakaton-gallery-HoopAndMerge/issues/3

**Требования:** R04 R07 R11. **Этап:** День 1.

### Цель

Дать безопасный вход и восстановление сохранённого положения по API v1.

### Что сделать

- [ ] Реализовать register/login/logout/me по api/contract.md; username lowercase, Unicode trim, пароль 8–128 байт без trim, безопасный KDF и соль.
- [ ] Cookie museum_session на 24 часа; в PostgreSQL только хеш токена. Замена отзывает только прежнюю cookie-сессию, logout идемпотентен.
- [ ] Точное сравнение Origin для POST/upgrade, запрет отсутствующего/null Origin; Secure отключается только явным local config.
- [ ] Порты уведомления об отзыве/истечении сессии и безопасный начальный/restored spawn; wire DTO и ошибки не раскрывают инфраструктуру.

### Приёмка

- Проверены 401 без сессии, username conflict, границы пароля/Unicode, чужой Origin и logout без cookie.
- Новый login сохраняет другие сессии аккаунта; истечение/отзыв передаются игровому соединению.
- Проверены rate limit login/register 10/60с/IP, no-store, X-Request-ID; SQL-интеграция на тестовой БД.

### Зависимости

Точка интеграции после: B01. Разработка через порты/fixtures может идти независимо; GitHub Blocked by используется только для реальных блокировок финального показа.

### Не входит

Клиентские формы — F01; transport WS — B04.

## B04. Backend. Реализовать защищённый WebSocket и lifecycle соединений

GitHub: https://github.com/MrDuckVC/hakaton-gallery-HoopAndMerge/issues/5

**Требования:** R03 R04 R11. **Этап:** День 1.

### Цель

Обеспечить упорядоченный транспорт для нескольких игроков с корректной заменой соединения.

### Что сделать

- [ ] Подключить закреплённый coder/websocket; authenticate+Origin до upgrade; первый event только world.snapshot, затем presence.
- [ ] Один WS на аккаунт, replacement4009 и left/joined; connection ID защищает новое состояние от старых reader/cleanup callbacks.
- [ ] Один writer, исходящая очередь <=1MiB, server event <=256KiB; inbound <=16KiB, binary1003, oversize1009, slow client1013; ping20s/pong10s.
- [ ] Лимит 32 подключения, UUID/дедупликация команд до10000, ошибки и rate limits из contract §9 без сброса reconnect; порты игровых сценариев реализует B05.

### Приёмка

- Тесты auth/Origin/replacement/session expiry/logout и slow consumer; другие клиенты не зависают.
- Snapshot не опережается другими событиями; события идут через единственный writer; нет гонок под -race.
- Неверный JSON/type/fields дают контрактную ошибку; 33-й новый аккаунт получает503 до upgrade.

### Зависимости

Точка интеграции после: B02. Разработка через порты/fixtures может идти независимо; GitHub Blocked by используется только для реальных блокировок финального показа.

### Не входит

Геометрия, готовность, переходы и содержимое игрового snapshot — B05.

## B05. Backend. Реализовать игровой state, движение, двери и сохранение

GitHub: https://github.com/MrDuckVC/hakaton-gallery-HoopAndMerge/issues/6

**Требования:** R03 R05 R07. **Этап:** День 1.

### Цель

Сделать сервер авторитетным источником позиции и переходов между залами.

### Что сделать

- [ ] Реализовать domain/usecase ready, epoch, seq, state snapshot и players.state10Hz; not-ready отклоняет игровые команды, но разрешает chat/cancel.
- [ ] Проверять finite coordinates, Y=0, yaw/pitch, скорость4m/s с dt<=0.25, sweep цилиндра radius0.3/height1.8 и границы; допустимый rotation независим от отклонённого движения.
- [ ] world.enter: дверь текущего зала, XZ<=1.5м и LOS; отмена вопроса через порт, транзакционное сохранение до entered, epoch+1/ack0/not-ready, entered до state.
- [ ] Позиция каждые5с и disconnect; DB failure периодического save ->close1011; недопустимое восстановленное положение сохраняется исправленным.

### Приёмка

- Проверены old/future epoch, stale seq, repeated ready, скорость после простоя, проход сквозь стену и касание пола.
- Ошибка сохранения перехода не меняет зал; старые команды/cleanup не меняют новое состояние.
- Позиция восстанавливается после рестарта, проигрыш не больше оговорённых5с; нет mutex на SQL/сети; -race проходит.

### Зависимости

Точка интеграции после: B03, B04. Разработка через порты/fixtures может идти независимо; GitHub Blocked by используется только для реальных блокировок финального показа.

## B07. Backend. Реализовать устойчивую очередь и историю генераций гидов

GitHub: https://github.com/MrDuckVC/hakaton-gallery-HoopAndMerge/issues/8

**Требования:** R09 R10 R11. **Этап:** День 1.

### Цель

Сохранять вопрос, состояние и итог генерации так, чтобы reconnect/restart не создавали дубль.

### Что сделать

- [ ] Миграции guide_generations/guide_memories; UNIQUE(user_id,request_id), payload fingerprint, partial UNIQUE одного queued/running на user, сериализованный FIFO:1running+8queued.
- [ ] guide.ask проверяет существующий key до ready/дистанции/очереди; новый ask валидирует guide/exhibit/LOS, текст<=2000, rate3/60с. accepted ставится в writer queue до worker.
- [ ] FSM queued/running/completed/failed, тайм-ауты120с/90с, limit8000, cancel/completion race с одним победителем; терминальный статус неизменен, completion+memory атомарны.
- [ ] GET generations и by-request, приватность/cursors/order; restart pending->SERVER_RESTARTED до обслуживания; disconnect/door/logout отменяют через порты, partial не память.

### Приёмка

- Повтор UUID+payload возвращает ту же Generation; другой payload конфликтует; параллельные ask не превышают лимиты.
- Проверены потеря accepted/completed, cancel race и корреляция failed/cancelled; failed сохраняет вопрос, но не partial.
- History чужого пользователя недоступна; тесты с fake clock/model и реальной тестовой БД; outage хранения не даёт ложного success.

### Зависимости

Точка интеграции после: B02. Разработка через порты/fixtures может идти независимо; GitHub Blocked by используется только для реальных блокировок финального показа.
